# Karu: what was built and how

This document describes the first working build of Karu, made from
[`KARU_PRODUCT_SPEC.md`](KARU_PRODUCT_SPEC.md) (Part 1) and
[`KARU_TECHNICAL_SPEC.md`](KARU_TECHNICAL_SPEC.md) (Part 2). It covers what exists, how each
part works, how to run it, and where the build differs from the spec. Section numbers such as
"Part 1 §4.3" point back into those specs.

Status at the time of writing: the API passes its 34 tests and `ruff` cleanly; the web app
passes `tsc` and ESLint, and `next build` succeeds with 49 app routes (48 pages plus the
ISR revalidate endpoint). Every flow below was run
end to end on a local machine with the fake providers. Nothing has been load-tested or
tested on real low-end Android phones yet.

---

## 1. The product in one paragraph

Karu is a marketplace for Indian handmade goods where every physical piece carries a
**Karu ID** (a QR tag such as `KRU-8F29A1QZ`). Scanning it opens a proof page that says,
above the fold, whether the piece is **Karu Verified**, who made it and where, and how it
was checked. Artisans list by voice: they take photos, speak about the piece in their own
language, and Karu writes the listing ("Snap + Speak"). Verification has three layers:
photo analysis, the maker's record, and a video of the piece being made. These combine
into one verdict. Selling is commission-free. Buyers pay through Razorpay and the money is
held until delivery and the return window pass.

## 3. Backend (`apps/api`)

### 3.1 Shape

One FastAPI process with one module per domain under `app/modules/`. Each module owns its
models, a `service.py` (business logic, no HTTP), a router, and its background tasks:

| Module | Responsibility |
|---|---|
| `auth` | Phone/email OTP, JWT access token plus rotating refresh cookie, CSRF, staff TOTP, sessions, data export/delete |
| `artisans` | Karu Passport, onboarding, profile, DigiLocker KYC (fake), Pehchan card check (web agent job), payout accounts, dashboard, PIN-code lookup |
| `media` | Resumable multipart uploads, photo processing, voice notes, making videos, speech-to-text endpoint |
| `ai_pipeline` | Snap + Speak: transcribe → extract → write listing in 3 languages → enhance photos → price advice; per-field regenerate; manual-form fallback |
| `catalog` | Listings, categories/crafts/clusters reference data, search, product pages, OG images, buyer card lookups |
| `karu_ids` | Karu ID issue and lifecycle, proof page payload, QR share images, A4 tag sheet PDF |
| `verification` | Three-layer engine, scoring, hard fails, periodic re-scan, staff evidence view |
| `pricing` | Market benchmarks by product fingerprint, handmade vs replica ranges, artisan price advice |
| `orders` | Cart → reservation → order, shipping, delivery, returns, timers |
| `payments` | Razorpay orders, webhooks, Route transfers on hold, refunds, hold release |
| `reviews`, `requests` | Reviews; "make again" requests and bulk opportunities |
| `notifications` | WhatsApp → SMS → in-app fallback, templated per language |
| `syndication` | Demo "list elsewhere" agent run (TinyFish) with a live view |
| `admin` | Staff console API: metrics, verification queue, listings, users, reports, config, costs, audit |
| `jobs` | Job status and progress over Server-Sent Events |

Cross-cutting code lives in `app/core/`: settings, database, IDs, transliteration, security,
errors, server-side i18n, versioned app config, the job runner, rate limits, audit log,
storage, imaging, video and ISR revalidation.

### 3.2 Data and IDs

- **Portable types.** Custom `JSONType` (JSON, with JSONB on Postgres), a UTC datetime type
  and native UUIDs. The same models run on SQLite locally and Postgres in staging.
- **UUIDv7** primary keys, so rows sort by creation time.
- **Human codes** use Crockford base-32, which avoids I, L, O and U so codes read well aloud:
  passports `KRP-XXXXXXXX`, Karu IDs `KRU-XXXXXXXX`, listing short codes (7 characters)
  and orders `KO-YYMMDD-XXXXX`.
- **Migrations.** Alembic `0001_initial_schema` was autogenerated from the models. On
  Postgres it also adds `pg_trgm` and `unaccent` with trigram indexes for search.
  `alembic upgrade`, `check` and `downgrade` were all run successfully.
- **Versioned app config** (`app_config` table plus `core/appconfig.py` defaults):
  verification weights and thresholds, pricing, commerce timers, limits, budgets, costs,
  passport rules, feature flags and categories. Staff edit it from the console, and every
  change is audited.

### 3.3 Background work

A small job system (`core/jobs.py`) registers handlers with `@handler("type")` and
schedules with `@periodic(...)`. Every job is a row in the `jobs` table, which stores its
status, progress and result, and the web app follows it over SSE.

- `TASK_MODE=inline`: jobs run on the API's own asyncio loop. Used for local development.
- `TASK_MODE=celery`: jobs go to Celery with one queue per job type. Each task runs in its
  own event loop with a NullPool engine, so connections are never shared across loops.

Periodic jobs cover: expiring reservations, shipping reminders, auto-cancelling unshipped
orders, auto-delivery, releasing payment holds, refreshing stale prices, re-scanning
verification, and purging expired OTPs and sessions.

### 3.4 Providers (the "fake by default" rule)

Every external service sits behind an interface with a real and a fake implementation.
An empty key selects the fake, which labels its output as such, so every flow works
offline (Part 2 §1).

| Interface | Real | Fake |
|---|---|---|
| LLM / vision | Gemini `generateContent` with `responseJsonSchema` | Deterministic rule-based extractor |
| Speech-to-text | Whisper or Gemini; the browser's on-device transcript is used as a fallback | Echoes the browser transcript |
| Web intelligence | TinyFish Search, Fetch and Agent (SSE), with `profile_id` for logged-in runs | Seeded price samples and image matches |
| Payments | Razorpay Checkout and Route (linked accounts, transfers on hold) | In-app test payment sheet |
| Messaging | MSG91 SMS, WhatsApp Cloud API, Resend email | Writes to the log; in dev the OTP is returned to the UI |
| KYC | DigiLocker | A fake consent page and callback |

### 3.5 Snap + Speak pipeline (`ai_pipeline/service.py`)

1. **Transcribe** the voice note in the artisan's language. If speech-to-text fails, use
   the transcript the phone made on-device.
2. **Extract** structured fields (title, category, craft, materials, technique, dye,
   dimensions, time to make, price) with a JSON schema. Missing fields become review
   notes ("We couldn't hear a price…").
3. **Write** the listing in the source language, English and Hindi, keeping the artisan's
   own phrasing where possible.
4. **Enhance photos & catalogue shots:** straighten, crop to 4:5 and 1:1, correct exposure
   and white balance, and generate 5 marketplace-style catalogue shots via Gemini using all
   original photos as references to keep the piece identical. Originals are kept for verification
   and the proof page, AI shots go in the gallery, and the artisan can remove any of them.
5. **Price advice** from the pricing module.

Progress is reported step by step over SSE ("Listening… Understanding… Writing…"). Each
field can be regenerated up to 10 times per listing per day. If extraction fails, the
artisan gets a manual form where every field still accepts voice.

### 3.6 Verification engine (`verification/`)

Three layers, each scored 0–100:

- **L1, photos:** a Gemini vision rubric for signs of handwork, plus perceptual hashes
  (pHash, Hamming distance ≤ 8 counts as a match) against Karu's own catalogue, plus a
  reverse-image web search. Matches on the artisan's own channels are allowed. Any other
  match costs up to 40 points.
- **L2, maker record:** a formula over KYC, Pehchan card, history, reviews and returns.
  New artisans get a fixed 50, so they are not penalised for being new.
- **L3, making video:** 20 s to 5 min. Keyframes are scored for process (0.40), match with
  the listed piece (0.35) and originality (0.25). The video's fingerprint is checked so
  one video cannot verify several pieces.

**Karu Score** = 0.35·L1 + 0.25·L2 + 0.40·L3. A listing is verified when the score is at
least 70 and the floors are met (L1 ≥ 40, L3 ≥ 50). Hard fails override the score:
reused video, stock-photo match, or a suspended maker. Buyers only ever see the verdict
and plain-language checks, never the numbers (Part 1 §5). Staff see everything. A
periodic job re-scans verified listings every 30 days, and a revocation is shown on the
Karu ID page with its date.

### 3.7 Pricing

For each listing, a **fingerprint** (category, craft, material, size band) is searched on
the web. Results are classified as handmade or replica, outliers are removed by IQR, and
p25 / median / p75 are computed per class. A range is only shown with at least 4 samples
in that class, and values are rounded to ₹10. Results are cached for 24 h. Artisans see
"below market / fair / above market" and a one-tap "use ₹X". **Karu never changes an
artisan's price.**

### 3.8 Commerce and payments

- Units are reserved for 15 minutes with a conditional `UPDATE … WHERE status='available'`,
  so two buyers can never get the same physical piece.
- Razorpay order → Checkout (UPI first) → webhook and client verify → capture → one Route
  transfer per artisan, **on hold**.
- The artisan marks the order shipped (packed with its Karu ID tag). Delivery is marked
  automatically 7 days after shipping unless the buyer confirms sooner. After the 7-day
  return window, the hold is released.
- Returns: the buyer requests, the artisan confirms receipt, and the refund is issued with
  the transfer reversed.
- Zero commission: the artisan's transfer equals the item price.

### 3.9 Security and privacy

- Passwordless OTP (6 digits, hashed, rate-limited, limited attempts). The access token is
  a short-lived cookie; the refresh token rotates and is scoped to `/api/v1/auth`. CSRF
  uses double-submit (`karu_csrf` cookie plus `X-CSRF-Token` header).
- Staff accounts must set up TOTP (pyotp) before any admin endpoint works.
- AES-GCM field encryption for legal name, date of birth, Aadhaar last 4, Pehchan card
  number and payout details (bank account/IFSC or UPI ID). Only the last 4 digits of
  Aadhaar are ever stored.
- Artisan location is stored rounded to about 1 km. Buyers see village and district only.
- Append-only audit log for every staff action and config change.
- DPDP-style export and delete (delete anonymises after 30 days; Karu IDs of sold pieces
  survive).
- Security headers and a strict CSP on the web app (`'unsafe-eval'` in dev only).

### 3.10 Tests

`apps/api/tests/`:

- **Scoring:** floors, hard fails, the new-artisan constant, L2 penalties, and
  non-accusatory tips.
- **Units:** IDs, Indian number grouping, localised dates, catalogue fallback,
  transliteration (Hinglish ↔ Devanagari) and pricing maths.
- **Flow:** the full marketplace path from onboarding through Snap + Speak, publishing,
  verification, buying, shipping and delivery to hold release. Also a last-unit race
  between two buyers, and a listing without a voice note.
- **Security:** cross-artisan access, CSRF, the OTP attempt limit, refresh-token rotation
  with reuse detection, webhook signatures and idempotency, the staff role + TOTP gate,
  and upload type checks.

**34 tests pass.**

## 4. Web app (`apps/web`)

### 4.1 Foundations

- **Next.js 16 App Router** with Turbopack. `/api/v1/*` and `/media/*` are rewritten to the
  API, so cookies and uploads are same-origin.
- **Design system** from Part 1 §9: indigo, haldi, peacock and khadi tokens in Tailwind v4
  `@theme`; Fraunces for display; per-script Noto fonts (Devanagari, Gurmukhi, Gujarati,
  Tamil, Malayalam, Naskh/Nastaliq for Urdu) loaded through `next/font`; taller line
  height for Indic scripts; logical CSS properties so Urdu renders right-to-left.
- **i18n:** URLs carry no locale. The locale comes from the `NEXT_LOCALE` cookie, then
  `Accept-Language`. Messages deep-merge over English, so a missing key shows English
  instead of breaking.
- **Data:** TanStack Query, a small API client (CSRF, silent refresh, typed errors), an SSE
  job hook, and resumable chunked uploads with client-side photo compression.
- **Offline (artisans):** a Dexie outbox keeps drafts (photos plus voice) on the phone, and
  a service worker uploads them with Background Sync when the network returns. The app
  shell is cached and there is an offline fallback page.
- **Voice:** Web Speech API for on-device transcripts, MediaRecorder for the audio sent to
  the server, a mic button on every text field in artisan flows, and optional read-aloud
  prompts.

### 4.2 Buyer marketplace (`app/(market)`)

Home (verified picks, crafts, makers, impact), categories, crafts and clusters, search
(transliteration-aware, so "banarsi" finds "बनारसी"), product pages (gallery and making
video, plain-language proof checks, maker story with an original/translation toggle, market
price bar, buy box, reviews, similar pieces, JSON-LD, OG image), maker profiles, cart,
checkout (Razorpay UPI-first, or the test sheet), order success with a shareable story
card, account (orders, returns, reviews, wishlist, following, addresses, notifications,
data export/delete), a bulk request form, and an impact page.

### 4.3 Karu ID proof page (`app/k/[karuId]`)

This is the page a QR tag opens, built for a cheap phone on a slow network: server-rendered,
cached per locale for 2 minutes, about 36 KB of HTML, with small client "islands" that get
their strings as props (no client i18n bundle). The verdict sits above the fold, followed
by the piece, the maker (voice clip and story), the proof (verified only, with a
tap-to-play making video), the piece's journey (made → listed → sold in a city →
delivered), market context, buy or request-again, and a report link. The cached page is
anonymous. After load, an island checks the session: owners see "This piece is yours"
and the "already sold" warning is hidden for them.

### 4.4 Artisan PWA (`app/sell`)

- **Onboarding** (`/sell/start`): language → phone OTP (Web OTP autofill) → name, date of
  birth, craft and location (GPS or PIN lookup), each by voice → a four-line consent in
  plain language → Karu Passport created.
- **Home:** a spoken summary ("2 orders to ship, ₹4,800 on the way"), task banners,
  profile completion, the offline queue, and products with price position and
  verification state.
- **New listing:** guided photo capture (with a darkness warning) → voice note → upload
  (or saved on the phone) → live pipeline progress → review (per-field regenerate, "use
  ₹X", manual fallback) → optional making video → quantity and returns → publish, which
  creates one Karu ID per unit.
- **Product:** overview, price advice, verification layers with plain next steps, stock
  and Karu IDs (QR tag sheet PDF), share images (WhatsApp status 9:16, Instagram 4:5,
  clean photo), pause/delete, and the demo syndication agent with a live view.
- Orders (pack with tag → shipped → returns), payouts (bank/UPI and hold timeline),
  passport (DigiLocker, Pehchan, photo, story, voice clip, page handle), requests and bulk,
  settings (language, read-aloud, notification channel, export/delete), and help.

### 4.5 Staff console (`app/admin`)

English only, behind TOTP. Overview metrics (refreshed every 30 s), the verification
queue with a run-detail sheet (every layer's score, sub-scores, evidence and image matches),
listings (hide/unhide, revoke verification, with a required reason), users (suspend/restore,
passport state), reports, bulk opportunities, the config editor (JSON per key, plus
"re-score with current config" as a preview or an applied change), AI/web cost tracking
against budgets, and the audit log.

### 4.6 Languages

English and Hindi are complete (972 keys). Punjabi, Marathi, Gujarati, Urdu, Tamil and
Malayalam cover the artisan app and every shared surface buyers meet first: badges, proof
checks, the Karu ID page, login, maker and passport cards (619 keys each). The remaining
buyer keys fall back to English. **These six were machine-assisted and are flagged
`_meta.review` for native-speaker review before any pilot.** `npm run check:i18n` reports
coverage, and a placeholder check confirmed every translated string uses the same
`{variables}` as English. The API has its own catalogue (`core/i18n.py`) for notifications,
review notes, price messages and share captions in all 8 languages.

## 5. Running it

### 5.1 Local (no Docker, SQLite, fake providers)

```bash
cd apps/api
python -m venv .venv && .venv/Scripts/pip install -r requirements-dev.txt   # .venv/bin on macOS/Linux
cp .env.example .env            # leave provider keys empty to use the fakes
.venv/Scripts/python -m app.scripts.seed
.venv/Scripts/python -m uvicorn app.main:app --port 8000
```

```bash
cd apps/web
npm install
npm run dev                      # http://localhost:3000
```

The seed creates 7 makers in 4 clusters, 21 products (14 verified, 7 not), 5 verified
passports, a buyer with an order and a review, and a staff account:

- Buyer: `+91 98888 00001`. Staff: `+91 97777 00001` (the seed prints the TOTP secret).
- With the fake SMS provider in development, the login screen shows the OTP.
- `python -m app.scripts.seed --live` uses the configured Gemini/TinyFish keys instead
  (slower, real market prices).

### 5.2 Staging-like (Docker)

```bash
docker compose -f infra/docker-compose.yml up --build
```

This runs Postgres 16, Redis, MinIO, the API (Alembic migrations), Celery worker and beat,
and the web app.

### 5.3 Checks

```bash
cd apps/api && .venv/Scripts/python -m pytest -q && .venv/Scripts/python -m ruff check app tests
cd apps/web && npm run typecheck && npm run lint && npm run check:i18n && npm run build
```

## 6. Where the build differs from the spec, and why

| Spec | Built | Why / what's needed |
|---|---|---|
| Postgres full-text search with trigram ranking | Python-side relevance ranking over SQLite locally; pg_trgm/unaccent indexes exist in the Postgres migration | Local dev without Docker. Switch ranking to SQL once staging runs on Postgres. |
| SigLIP image embeddings for similarity | `lite_embedding` (colour/texture features) plus pHash | No GPU or `ml` worker deployed yet. Swap in SigLIP/CLIP behind the same function. |
| DigiLocker Aadhaar KYC | Fake consent page and callback | Needs a DigiLocker partner agreement. |
| UPI payouts to artisans | Bank account payouts; UPI shows "starting soon" | Razorpay Route linked accounts with UPI settlement must be enabled on the account. |
| next-intl plugin | next-intl used through an alias in `next.config.ts` | The plugin pulls in `@swc/core`, whose native binary would not load on this Windows machine. Behaviour is the same. |
| Staff console in all languages | English only | Internal tool. Only staff use it. |
| Real product photos and making videos | Procedural placeholder images and placeholder video files in the seed | **Replace with real, permissioned media before any public demo.** |
| Real OTP delivery | In development with the fake provider, the OTP is returned to the UI | Configure MSG91/WhatsApp keys; the dev code is never returned once a real provider is set. |
| Six regional languages complete | Artisan app and shared surfaces translated; other buyer pages fall back to English | Native review, then translate the remaining buyer keys. |

Other notes:

- `npm run gen:api-types` expects a `packages/api-types` folder that does not exist yet.
  The web app uses hand-written types in `lib/types.ts`.
- Secrets are never committed: `.env`, `.venv`, `var/` (SQLite and local media) and
  `node_modules` are git-ignored.
